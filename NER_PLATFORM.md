# NER Smart Logistics & Accessibility Intelligence Platform

An extension of the existing LogiRush multi-modal route selector, adapted for disaster-
resilient logistics across the eight North Eastern states of India (SIH 2026).

The original cross-border optimiser is **untouched and still works** — `POST /api/find-routes`
behaves exactly as before, and a test asserts its objective vector is unchanged. Everything
described here is additive.

---

## Read this first: what is real and what is not

| Component | Status |
|---|---|
| Accessibility scoring formula & categories | Real, deterministic, unit-tested |
| Risk-aware routing (A\* extension, Pareto search) | Real, working algorithm |
| Cargo priority profiles | Real — verifiably change the selected route |
| Shipment lifecycle, route snapshots, replanning | Real, database-backed |
| Incident reporting, verification, idempotent offline sync | Real, database-backed |
| Offline queue (IndexedDB) + service worker + PWA | Real |
| **Road network data for NER** | **Sample data.** Real town names/coordinates and real highway corridor names, but hand-built — not an official road network dataset |
| **Rainfall** (observed 24 h, forecast 48 h) | **Live.** Real precipitation from Open-Meteo, read at each corridor's midpoint. Real meteorological data — *not* an IMD product |
| **Weather risk** | **Live, derived.** A deterministic ladder over IMD's published rainfall bands, applied to the live rainfall above |
| **Risk figures** (landslide/flood/incident/delay) | **Synthetic.** Not from GSI, CWC, NDMA, ASDMA or state PWD |
| **Disaster prediction model** | **Real Random Forest, trained on synthetic data.** The pipeline is genuine; the probabilities are not validated real-world forecasts |

Every API response carries `"data_source": "mock"`, every prediction carries its `model_type`,
the dashboard shows the model's provenance inline, and a disclaimer banner appears on every
screen. Do not present any figure from this system as official government data.

**`GET /api/ner/data-sources` answers this input by input**, and the web console renders it at
`/data-sources` ("Where this data comes from", reachable from the disclaimer on every screen).
It is generated by `src/data_processing/data_sources.py`, which sits next to the loaders, so
the claim shown to an operator cannot drift away from the code that reads the data. Each entry
declares a trust level — `live`, `sample`, `synthetic` or `derived` — plus what it feeds and
what would replace it in a real deployment.

The distinction that matters most on that screen: **rainfall is live, and it is still not an
IMD feed.** `rainfall_mm_24h` and `forecast_rainfall_mm_48h` are now real precipitation from
Open-Meteo, which serves the national weather services' own models (DWD ICON, ECMWF, NOAA
GFS). That is genuine meteorological data and it is not a product of the India Meteorological
Department, so the manifest names IMD only twice: as the classification whose bands the risk
ladder uses, and as the upstream a real deployment would source rainfall from. Tests pin that
it never appears as the origin (`tests/test_data_sources.py`, `tests/test_live_weather.py`).

Rainfall's trust level is the one that changes at runtime — `live` while the feed answers,
`sample` when it does not — and the manifest reads it from the running provider rather than
declaring it, because a hard-coded answer would be wrong half the time and wrong in the
direction that flatters the platform.

See [Live rainfall](#live-rainfall-module-2b) for how it is wired.

**To make the predictions real:** replace the synthetic label generation in
`disaster_prediction.py::generate_training_data` with actual historical event records, and
implement a real `NERDataProvider`. No other code needs to change.

## Architecture

```
   ner_data_provider.py       disaster_prediction.py        incidents (DB)
   (roads, terrain, weather)  (Module 2: Random Forest)     (Module 5)
             |                          |                         |
             +------------+-------------+-------------------------+
                          |
                accessibility_service.py
            (blending + deterministic business rules)
                          |
                accessibility_engine.py
              (Module 1: pure formula, no ML)
                          |
                 ner_graph_builder.py
          (normalised 0-100 objective costs per edge)
                          |
                    ner_router.py  <---- cargo_profiles.py (Module 4)
        (Module 3: extends MOAStar, 5 objectives)
                          |
                  routing_service.py
        (single planning entry point + condition cache)
                    /            \
          /api/ner/plan-route   /api/ner/shipments
```

**AI Usage Policy compliance.** Machine learning appears in exactly one file
(`disaster_prediction.py`) and only predicts future disruption probability. Accessibility
scoring, route selection, incident verification and all business rules are deterministic.
`accessibility_engine.py` never imports the model; the model never sees an accessibility score.

### Four design decisions worth explaining in a judging session

**1. Risk is a bottleneck, not a sum.** Accessibility, risk and reliability accumulate as a
running *maximum* across a route; time and cost accumulate as sums. If risk were summed it
would grow with segment count, the shortest path would win every objective at once, and the
cargo profiles would have no visible effect. The bottleneck is also the correct model: a
convoy is stopped by its single worst stretch, not by an arithmetic total.

**2. Impassable roads are removed from the graph, not penalised.** A closed road or a verified
severity-5 blocking incident excludes the segment entirely, so the router physically cannot
route through it — stronger than a large penalty the optimiser might still accept.

**3. Risk attribution is wide; closure is narrow; both are bounded.** A nearby incident raises
risk on every corridor within 12 km, but closes only the one corridor it was attributed to at
ingest. Without that split, a single landslide reported near a junction would strand an entire
region. Attribution itself stops at 30 km (`INCIDENT_SNAP_RADIUS_KM`): beyond that a report is
recorded and mapped at its own coordinates but belongs to no corridor and affects no route.
An unbounded "nearest corridor" is not attribution but a guess that always answers — a report
filed from Mumbai matched a corridor in Assam 1,756 km away and, because an explicitly
attributed report skips the proximity check, could have closed it. Every surface now states
the corridor by name and the distance to it, so a mistyped coordinate is visible to the
person who typed it: the web form previews the match live (`GET /api/ner/incidents/preview`)
and draws the point on a map, the field app reports it on sync, and the review queue flags an
off-network report before anyone signs it.

**4. Alternatives are re-scored before ranking.** Alternative routes are found by penalising
already-used segments and re-searching. Those penalties distort scores, so every route is
re-scored on the clean graph before ranking — otherwise a better alternative could be
displayed below a worse one.

## Frontend

React 19 + Vite + Tailwind v4 + Leaflet. Seven screens:

| Route | Purpose |
|---|---|
| `/dashboard` | KPIs, risk-vs-accessibility scatter, state comparison, model provenance |
| `/accessibility-map` | Network map with filters, legend, corridor drill-down |
| `/shipment-planner` | Plan a route; alternatives, explanation, live map preview, save as shipment |
| `/shipments` | Shipment list, status advance, re-check route against current conditions |
| `/incidents` | Verification queue — verify/reject reports |
| `/report-incident` | Field reporting form; works fully offline |
| `/data-sources` | Where every number comes from: each input, its trust level, its upstream |

Notes on the build:

- **No charting library.** The four charts are hand-written SVG. A charting dependency would
  add 100-200 kB to a bundle that field users may load on a weak connection.
- **Mobile-first.** Responders work from phones, so every screen is tested at 390 px with an
  automated no-horizontal-overflow assertion.
- **Offline queue is global.** Pending report count shows in the header on every screen, not
  just the report page — a queue you can only see in one place is one people forget.
- **Accessibility.** Skip link, labelled controls, visible focus rings, `prefers-reduced-motion`
  respected, colour never the sole carrier of meaning (scores print numerically too).
- One shared band table (`src/lib/accessibility.js`) mirrors the backend's category
  thresholds, and an e2e test asserts the two agree.

## Deployment

**Backend** — Docker (`routeOptimiserBackend/Dockerfile`) or Procfile, running gunicorn.
`render.yaml` is a ready Render blueprint; Railway works from the same Dockerfile. Set:

- `DATABASE_URL` — Postgres/Neon connection string (omit to use local SQLite).
  `postgres://` URLs are rewritten to `postgresql://` automatically.
- `CORS_ORIGINS` — your deployed frontend URL (defaults to `*`, which you should not keep).

**Frontend** — Vercel, using `routeOptimiserFrontend/vercel.json`. Set `VITE_API_BASE_URL` to
the deployed backend URL. The SPA rewrite is configured so client-side routes survive refresh.

**Database** — tables are created at startup (`init_db()`), so no migration step is needed for
the first deploy. If the database is unreachable the app still serves routing and accessibility
endpoints, with incident features degraded rather than failing.

**CI** — `.github/workflows/ci.yml` runs backend tests, frontend lint/build, and the full
browser e2e suite against a real backend on every push.

## Live rainfall (Module 2b)

Rainfall was the largest single assumption in the platform. `rainfall_mm_24h` and
`forecast_rainfall_mm_48h` are the disaster model's two strongest features and, through
`weather_risk`, a quarter of every accessibility score — and both were hand-authored values in
a CSV. The give-away was in the numbers themselves: every rainfall figure in the file is a
multiple of 5, as are all 160 corridor risk values. Real measurements do not do that; people
picking numbers do.

They are now real, from **Open-Meteo** — free, keyless, and serving the national weather
services' own model output (DWD ICON, ECMWF, NOAA GFS).

**Where it is wired, and why that is the whole point.** The substitution happens behind the
`NERDataProvider` interface (`LiveWeatherNERDataProvider`), not beside it. An endpoint that
reports live weather proves an HTTP call works while the map, the risk scores and the routing
carry on running off the CSV — the platform would look identical from outside and decide
exactly the same things. Overriding `get_segment_features()` and `get_road_segments()` instead
means the corridor colours, the model's probabilities and the chosen route all move when it
actually rains. Measured against the snapshot on the day this landed: **29 of 32 accessibility
scores and 32 of 32 flood probabilities changed.**

This is also the first real test of a claim the original data provider made in a docstring —
that a real feed could be swapped in with "nothing in accessibility_engine.py or the API layer
needing to change". Nothing did.

**How the numbers are derived.**

| Field | From |
|---|---|
| `rainfall_mm_24h` | summed hourly precipitation over the last 24 h |
| `forecast_rainfall_mm_48h` | summed hourly precipitation over the next 48 h |
| `weather_risk` (0-100) | a deterministic ladder over the two above, using IMD's published rainfall bands |

Corridors are read at their **midpoint**, not their endpoints: a segment can be 600 km long,
and the rain that closes it falls on the road rather than in the city it ends at.

`weather_risk` stays ML-free and reproducible, as the AI Usage Policy requires of anything
feeding an accessibility score. The bands are IMD's own classification — light, moderate,
heavy, very heavy, extremely heavy — because inventing a private scale when the national
meteorological service has published one would be arbitrary and harder to defend. The
classification is official; the rainfall it is applied to is Open-Meteo's, and the platform
says so on every surface that shows it.

**Failure is designed for.** Every fetch is time-boxed (4 s), cached (15 min), and batched into
a single request for all 32 corridors. On any error the platform silently keeps the CSV
snapshot it already had, and the provenance manifest flips that input back to `sample` and
reports the error. A weather API having a bad afternoon must never be able to take routing
offline — and it must never be able to make the platform quietly overstate itself either.

One bug this surfaced: on macOS, Python does not use the system trust store, so an Anaconda or
Homebrew interpreter that has never run `Install Certificates.command` fails every HTTPS
request with `CERTIFICATE_VERIFY_FAILED`. Because this module degrades gracefully, that
presented as "live weather unavailable" — indistinguishable from the API being down, and it
would have been diagnosed as a broken feature rather than a missing CA bundle. The client now
builds its TLS context from `certifi`. Verification is never disabled; an unverified HTTPS
request would be worse than no request, since the entire point is trusting the numbers that
come back.

| Variable | Default | Effect |
|---|---|---|
| `NER_LIVE_WEATHER` | `1` | `0` pins the shipped snapshot — offline work, reproducible runs, and the test suite |
| `WEATHER_CACHE_TTL_S` | `900` | how long a fetch is reused |
| `WEATHER_TIMEOUT_S` | `4.0` | how long a fetch may block before falling back |

`GET /api/ner/weather` reports the live rainfall per corridor with its IMD band, the derived
risk, the age of the fetch, and an unprompted `"official_imd_feed": false`.

The test suite pins the snapshot (`tests/conftest.py`): a suite whose numbers depend on this
afternoon's weather in Meghalaya is not a suite. The live path is tested with the HTTP layer
stubbed (`tests/test_live_weather.py`), including the fallback and the honesty of the manifest
in both states.

**What is still not live.** Landslide susceptibility, flood history and road status remain
sample or synthetic; they need GSI, CWC and a state PWD feed respectively. Making one input
real is only worth doing if the others stay honestly labelled, and they do.

### One database, two clients

The web console and the NER Field Reporter app are two programs that have to behave as one
system: a report filed on a phone at a landslide must appear in the review queue the control
room is watching. There is no synchronisation between them to build, because there is nothing
to synchronise — both write to the same `incidents` table through the same endpoints
(`POST /api/ner/incidents`, `POST /api/ner/incidents/sync`) on the same backend.

Which means the entire connection is one setting in each client, and getting it wrong is the
only way the two can appear unlinked:

| Client | Setting | Value |
|---|---|---|
| Website | `routeOptimiserFrontend/.env` → `VITE_API_BASE_URL` | the backend URL |
| Field app | `nerFieldApp/.env` → `EXPO_PUBLIC_API_BASE_URL` | **the same backend URL** |
| Backend | `DATABASE_URL` | one Postgres URL, on every instance |

The failure this causes is quiet and looks like a bug in the code. The app, left unconfigured,
infers its backend from the address Expo is serving on — your laptop. That is the right default
while developing and wrong the moment the website points at a deployed backend: reports filed
from the phone land in the laptop's SQLite file, the deployed console reads a different
database, and each half works perfectly while showing nothing the other filed.

Three things make the link visible rather than something you have to take on trust:

- **The app's Sign in screen → Test connection** reports the address *and the number of reports
  that backend holds* — `GET /api/ner/incidents` now returns `total` alongside the page-limited
  `count`. A surprising `0` is the clearest possible sign of pointing at the wrong backend.
- **Every report records which client filed it** (`source`: `app` | `web` | `api`). The review
  queue shows `via field app` on the row and counts them in the header. An unmarked or
  unrecognised value is recorded as `api` — never guessed at, and never a reason to lose a
  report.
- **`/data-sources` reports the live database**: how many reports it holds, split by client,
  and which engine they are stored in.

Both clients keep working with no account and no configuration; this is about where the data
lands, not who may send it.

**A real bug this exposed.** `incidents.image_url` was `VARCHAR(512)`, and both clients attach
the photograph inline as a base64 data URI — tens of thousands of characters. SQLite ignores a
declared length, so every photographed report worked locally and on any SQLite demo. On the
Postgres database the two clients actually share, Postgres does not ignore it:
`value too long for type character varying(512)`. Every photographed report failed, on exactly
the deployment where the two clients are connected — which is to say the bug was invisible
until the moment the feature mattered. The column is now `Text`, and `schema_sync.py` widens an
outgrown bounded `VARCHAR` on an existing database, since `create_all()` never retypes and the
symptom cannot be reproduced on SQLite. Verified against PostgreSQL 14: the old schema raises
`DataError`, the upgraded one stores a 60 KB data URI and the report appears in the queue.

Flask now also carries a `MAX_CONTENT_LENGTH` (16 MB, `MAX_CONTENT_MB` to change it) with a
JSON 413 handler, so an oversized queue flush is refused with a message the reporter can read
rather than buffered.

### Deviation from the spec, flagged deliberately

The spec's deployment section asks for **FastAPI** and **React + TypeScript**. This build stays
on **Flask** and **JavaScript**, because the spec's own development rules say never to rewrite
working functionality, and porting frameworks would touch every file for no behavioural change.
All intelligence logic is framework-agnostic and would port largely unchanged. PostgreSQL,
Neon, Vercel and Railway/Render are supported as specified. Cloudinary is not wired in —
incident images are accepted as a URL (`image_url`), so adding an upload provider is a frontend
change plus one storage call, with no schema change.

## Bugs this round found

Three of these were silent — the interface reported success in every one of them, which is
what let them survive.

**Incidents were filed against corridors they were nowhere near.** `nearest segment` had no
maximum distance, so any coordinate on Earth matched something: a report from Mumbai landed
on a corridor in Assam 1,756 km away, appeared on the map as that corridor's problem, and —
because an explicitly attributed report skips the proximity check used for risk — a
severity-5 landslide "in Mumbai" could have closed a highway in Assam once verified.
Attribution now stops at 30 km, the distance is stored and shown everywhere a report is, and
the report form previews the match on a map before it is submitted. A stored attribution from
beyond the radius can no longer close anything either, so upgrading a database that already
contains one is safe.

**The offline queue silently dropped reports.** `offlineQueue.js` opened the IndexedDB
database at version 1 while `offlineStore.js` opened the same database at version 2. Once
anything touched the reference cache — the offline-readiness panel does, on the report screen
— every queue operation threw `VersionError` and the report was lost, while the form said it
had been saved to the device. That is the worst failure this feature has: a field user with
no signal is told their landslide report is safe and it is not there at all. The schema now
lives in one module (`src/utils/idb.js`) that both import, so the two cannot disagree again.

**A signed-in reporter was recorded as anonymous.** `POST /api/ner/incidents` was missing
`@optional_user()`, so `g.user_id` was never set and every web submission stored
`reported_by_id = NULL`. The no-self-verification rule depends on that column, so the rule
quietly applied to nothing filed through the web app.

**Two dependencies were installed and never imported.** `recharts` and `lucide-react` cost
37 MB of `npm install` and a pre-bundling pass on every dev server start to ship no bytes.
The charts are hand-written SVG on purpose (`components/charts.jsx`); both are gone.

**Sign-in was unreachable on a phone.** The secondary navigation sheet — which holds sign-in
— existed only inside the desktop rail, and the rail is `hidden md:flex`. A District Verifier
holding a phone could not sign in, so the review queue they are there to clear was
unreachable from the device they actually carry. The trigger is now in the mobile top bar
too.

**The end-to-end suite had stopped testing the application.** It asserted against headings
the redesign removed, a corridor table that became a list, `<select>` elements that became
searchable comboboxes, and a hamburger menu that became a tab bar. Worst of all, its check
that cargo profile changes the recommended route compared a label showing only the endpoints,
so it compared `Guwahati→Silchar` with `Guwahati→Silchar` and could never fail — the route
card now names the waypoints (which an operator wanted anyway), and the check reads those.
Verification also became an authenticated, two-signature action without the suite following,
so it now signs in as the seeded verifier and controller and asserts that one signature
leaves the corridor open.

## Performance

The spec asks for an accessibility refresh under 30 seconds and a route calculation under 3.
Both were met, but by a wide enough margin that nobody had looked at where the time was
actually going — and the answer was: almost all of it in one avoidable place.

**Model inference was per-segment.** `assess_all_segments` called the Random Forest once for
each of the 32 corridors, and each call re-derived the forests' feature importances by walking
all 120 trees, twice, to explain a single prediction. Assessing the network cost **1,080 ms**,
and every dashboard load, every map refresh and every route plan waited on it. Predicting all
32 rows in one call and computing the importances once per fit brings that to **~21 ms** — a
50× improvement with identical outputs (`predict` now delegates to `predict_many`, so there is
only one inference path to be right).

**The cache had no single-flight guard.** The dashboard opens five requests at once; on an
expired cache all five rebuilt the network in parallel. One rebuilds now and the rest read the
result, so five simultaneous cold requests cost one rebuild — the slowest of five concurrent
dashboard calls is **11 ms**.

**Start-up cost landed on the first visitor.** Loading two persisted forests takes ~1.5 s, and
the first batch prediction pays NumPy's warm-up on top. That is now done on a background
thread at boot, before anyone asks. Flask's debug mode — which doubles start-up and wraps
every response — is off unless `FLASK_DEBUG=1`.

Measured on the sample network (27 nodes, 32 corridors), warm:

| Endpoint | Time | Payload |
|---|---|---|
| `/api/ner/dashboard` | 7 ms | 4.9 kB |
| `/api/ner/analytics` | 2 ms | 5.9 kB |
| `/api/ner/segments` | 2 ms | 29 kB |
| `/api/ner/locations` | 2 ms | 3.2 kB |

**On the frontend, every page was in the first download.** Leaflet, the planner, the review
queue and the dashboard all loaded before the landing page could paint. Routes are lazy now
and the vendors are split, so the first load is **229 kB (72 kB gzipped) instead of 502 kB
(151 kB)** and Leaflet's 155 kB arrives only with the two screens that draw maps. `recharts`
and `lucide-react` were listed as dependencies and imported by nothing — 37 MB of install and
a pre-bundling pass on every dev start to ship no bytes; both are gone (the charts are
hand-written SVG on purpose, see `components/charts.jsx`).

The API client now de-duplicates in-flight GETs and holds reads briefly — minutes for data
that changes only on deploy, seconds for live conditions, cleared entirely by any write — so
moving between screens stops refetching the same corridor assessment. On the map, the glass
panels are `contain: paint` and composited, the tile filter declares `will-change`, and the
corridor and town layers are memoised, so panning no longer re-runs a five-stage filter chain
and a backdrop blur over every frame.

## Module 4b — Weight-aware multimodal transport (added)

### The defect this fixes

Cost was previously `distance_km × FREIGHT_RATE_INR_PER_KM`. Weight never entered the
calculation, so a 100 kg consignment and a 10 tonne consignment on the same corridor were
quoted the identical price, and the `weight_kg` field on the planner was decorative.

### How pricing works now

`src/modeling/transport_modes.py` prices a consignment from three terms, all of which move
with weight:

| Term | Formula | Why |
|---|---|---|
| Dispatch | `fixed_inr × fleet` | Booking and positioning each vehicle |
| Running | `per_km_inr × distance × fleet` | Fuel, driver, wear per vehicle |
| Haulage | `per_tonne_km_inr × tonnes × distance` | Scales with the load actually carried |
| Handling | `handling_inr_per_t × tonnes` | Loading and unloading, charged once |

`fleet = ceil(weight / capacity)`, which is why cost **steps** at capacity boundaries: on the
Guwahati–Dibrugarh corridor 9,000 kg is one truck at ₹35,015 and 9,010 kg is two at ₹60,725.
Between boundaries the haulage and handling terms move it continuously, so 1,000 kg and
1,010 kg also differ. Both behaviours are deliberate and covered by tests.

### The eight modes

Road classes (pickup 1 t, LCV 4 t, 9-tonne truck, multi-axle 25 t), rail (NF Railway,
railhead to railhead), inland waterway (NW2 Brahmaputra, river terminals), helicopter airlift,
and porter/mule for last-mile into cut-off villages. Railheads, river terminals and airheads
are curated from real NER infrastructure and listed explicitly in `transport_modes.py`.

### Why each mode gets its own route

Each mode declares `min_accessibility` — the corridor quality it needs. `transport_planner.py`
prunes the network to the segments a mode can actually operate on and re-routes on that
subgraph. A segment is removed, not penalised: a road that cannot carry a 25-tonne truck is
not an expensive option for that truck, it is not an option.

The effect is visible on Siliguri → Aizawl: a pickup takes the direct 1,215 km corridor via
Silchar, while the 9-tonne truck is pushed onto a 1,409 km route via Kohima and Imphal
because the direct corridor falls below its accessibility floor. That difference in routing
is also why an LCV convoy can beat a single truck on price for that pair.

### Ranking

Options are scored with the cargo profile's own objective weights over min-max normalised
time, cost, risk, accessibility and reliability. A premium ceiling (widening with urgency and
cargo criticality) stops a profile's non-cost priorities from recommending a ₹12 lakh airlift
for a load a ₹75,000 truck can carry — the airlift stays listed and priced, but only takes
the top slot when urgency justifies it. So critical medicine gets the helicopter, and routine
general cargo does not.

### API

- `GET /api/ner/transport-modes` — rate cards, capacities, accessibility floors
- `POST /api/ner/plan-route` — now accepts `weight_kg`; returns `transport_options`,
  `recommended_transport` and `weight_sensitivity` alongside the existing fields
- Shipment create and replan carry the consignment weight through, so a replan compares
  like for like

## Module 6b — Full offline field kit (extended)

Interior Arunachal, Mizoram and Manipur routinely have no usable mobile data, which is
exactly where a blocked road most needs reporting. The app now degrades to reduced freshness
rather than to an error screen.

| Capability | Where |
|---|---|
| Reference data cached on device (locations, corridors, cargo profiles, rate cards) | `utils/offlineStore.js` |
| Route planning entirely on-device, mirroring the server's scoring | `utils/offlinePlanner.js` |
| Photo capture, downscaled on device before storing or sending | `utils/offlineStore.js` → `compressImage` |
| Durable idempotent report queue (pre-existing, retained) | `utils/offlineQueue.js` |
| Field-readiness panel: what works offline, what is queued | `components/OfflineReadiness.jsx` |
| Cold-start offline: hashed assets precached on first visit | `public/sw.js` |
| Background sync when the OS reports connectivity restored | `public/sw.js` + `SyncContext` |

The offline planner deliberately mirrors the server: same five normalised objectives, same
normalisation references, same cargo weight vectors and rate cards (both cached from the API,
so they cannot drift). Rail, waterway and air are listed as needing a connection rather than
guessed at, because terminal and schedule availability is not something the device can know.
Every offline result is stamped with the age of the data it used and shown behind an explicit
banner — a three-day-old view of a monsoon-hit corridor is a starting point, not a fact.

## Design system — dark geospatial command centre

The UI previously inherited a neon cyan/pink gradient from the template it was built on. It
read as a product landing page rather than something an operations officer stares at for
eight hours during a monsoon. The rework treats the screen as an instrument.

### Colour is assigned by the job it does

| Job | Encoding | Where |
|---|---|---|
| Magnitude — how impeded a corridor is | One hue, stepped by lightness | Map corridors, accessibility badges |
| State — open / repairing / blocked / closed | Reserved status roles + icon + label | Badges, alerts, incident markers |
| Series identity — transport modes | Fixed categorical order | Cost-versus-weight curve |

Every palette was validated with a script rather than by eye, against this app's own panel
surface (`#0f141b`):

- **Impediment ramp** — `#5a4c3c → #8f6129 → #c9782b → #f0a24c → #ffcd93`. One hue (11°
  spread), monotone lightness, every adjacent gap ≥ 0.06 L, dimmest step 2.23:1 on the
  surface.
- **Series palette** — `#3987e5, #d95926, #199e70, #c98500`. Worst adjacent pair measures
  ΔE 8.4 under colour-vision deficiency and 19.8 for normal vision, both above the gates.

The **previous scale was a rainbow** — green, lime, yellow, orange, red. It failed on its
own terms: lime against yellow measured ΔE 2.3 under protanopia (8 is the target), so two
adjacent bands were indistinguishable to a red-green colourblind operator, and because amber
is the lightest of those hues the scale did not read as ordered in greyscale or through a
projector either.

The ramp's range is deliberately wide. Real corridor scores cluster mid-scale, and a narrow
ramp rendered every road the same orange — technically correct, operationally useless.
Pushing the healthy end near-neutral means sound corridors go quiet and the eye lands on the
ones that are failing.

### Colour is never the only channel

Corridors carry condition in **stroke width and dash pattern** as well as hue, so a degraded
road is thin and broken even in greyscale. Status badges carry a **glyph**; accessibility
badges carry a **band icon**. Redundant colour was removed where a second channel already
said the same thing: state-comparison bars are neutral because length already encodes the
value, and scatter dots are neutral because position does.

### The map is the instrument

A near-monochrome dark basemap keeps the corridor overlay the only saturated layer. Because
tiles are exactly what a field connection loses first, the map degrades honestly: a
coordinate graticule and permanent town labels keep the network readable with no basemap at
all, and a notice says so rather than presenting an empty rectangle as terrain. Town labels
are ranked — eleven regional hubs always, minor towns from zoom 8 — because 27 names at once
collapse into an unreadable smear.

### One bug worth recording

Design tokens are declared twice: as hex (for inline styles, SVG fills and anything JS
reads) and as bare RGB channels for Tailwind. The channel form is not redundant. Tailwind
compiles an opacity modifier to `rgb(<colour> / <alpha>)`, which is only valid when
`<colour>` is channels — hand it a finished `var(--accent)` and the declaration is invalid,
so `bg-accent/10` silently computes to **transparent**. It renders as a washed-out UI with
no error anywhere, and it was caught by reading computed styles in a real browser, not by
looking at the code.

### Verified, not assumed

All six screens are driven in headless Chromium at 1440 / 768 / 390 px: no horizontal
overflow at any width, one `<h1>` per screen, skip link first in tab order, a visible focus
ring, no image missing `alt`, and every interactive control at least 32 px tall under a
coarse pointer.
